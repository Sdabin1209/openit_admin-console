# ADR 0024: 화면 요청 대기 상한을 경로별로 둔다 (D125)

- 상태: 채택(2026-11-02). [ADR 0010](0010-시간-제한과-한도-상수.md)의 "요청 시간 제한 15000 ms"를 대체한다(0010의 나머지 상수는 그대로).

## 맥락
사용자 결정 D125: 목표(SLO)와 실패 판정을 나눈다. gateway의 사람 화면 경로 상한이 release-gate 180초, question-authoring 120초, ops-feedback 60초(연결 1초 별도)로 바뀌었다. 사슬은 화면 > gateway > 서버여야 한다(`boundary-contracts/CONVENTIONS.md` "시간 상한 사슬"). 15초는 근거 없는 값이었고 새 gateway 상한보다 짧아 화면이 먼저 포기해 같은 요청이 이중 처리될 수 있다.

## 결정
- release-gate 경로(제출 조회·승인·활성화·롤백·릴리스 목록): 190초(`RELEASE_GATE_TIMEOUT_MS`).
- ops-feedback 경로(실패 사례 목록·조회·trace·검토): 70초(`OPS_FEEDBACK_TIMEOUT_MS`).
- 이 콘솔은 question-authoring을 부르지 않는다. 130초 값은 쓰지 않는다.
- 두 값은 `app/wiring/gateway.ts`가 클라이언트별로 넣는다. 하나뿐이면 가장 긴 190초로 했겠지만, 검토 화면이 60초 표준보다 3배 넘게 멈춘 채 기다리게 되므로 나눴다.

## 왜
값은 계약 시간표의 것이다(gateway 상한 + 10초 여유). 계약 쪽 근거는 프록시·LB 표준 60초(nginx `proxy_read_timeout`, AWS ALB idle timeout)와 측정 최악값(승인 128초) 위의 여유다. 이 영역은 시간을 재지 않았다.

## 검토한 대안
- 190초 하나: 단순하지만 검토 경로의 대기가 불필요하게 길다.
- 15초 유지: gateway보다 짧아 이중 처리를 부른다.

## 결과
느린 승인에서도 화면이 응답을 받는다. 대신 정말 멈춘 요청은 최대 190초 뒤에야 오류가 된다. 화면에는 요청 중 표시("불러오는 중…", "전송 중…")가 즉시 나오지만 10초 뒤 "처리 중입니다" 안내는 아직 없다(열린 것, STATUS.md).

## 되돌리는 조건
계약 시간표의 값이 바뀌면 따라 바꾼다. `tests/exposure.test.ts`가 gateway 선언 < 화면 값을 확인한다.
