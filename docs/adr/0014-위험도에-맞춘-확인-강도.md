# ADR 0014: 되돌릴 수 없는 승인에 더 강한 확인, 되돌릴 수 있는 활성화·롤백은 단순 확인

- 상태: 채택(2026-10-29, 표준성 점검 E2·E4, 헤드 결정표 2절). [ADR 0004](0004-승인-확인창-흐름.md)의 "승인에는 입력을 더 요구하지 않았다"와 [ADR 0007](0007-활성화-롤백-확인-문구.md)의 "대상 릴리스 ID 입력"을 대체한다. Supersedes(일부): 0004 대안 3항, 0007 결정 첫 문장.

## 맥락
점검에서 확인 강도가 위험도와 반대였다. 승인·반려는 기록되면 되돌릴 수 없다(확인창 문구). 활성화는 이 화면의 롤백으로 되돌릴 수 있고(`docs/adr/0007`의 되돌리기 안내), 롤백도 다시 활성화로 되돌릴 수 있다. 그런데 승인에는 확인창 한 번뿐이고 활성화·롤백에는 대상 ID 입력이 있었다. 또 승인은 모달 `<dialog>`, 활성화·롤백은 페이지 안 인라인 폼으로 방식이 달랐고 그 이유가 적혀 있지 않았다.

## 결정
1. **승인·반려**: 확인창(`<dialog>` 모달)에서 **제출 ID를 그대로 입력해야** 확정 버튼이 켜진다(앞뒤 공백만 무시). 컨트롤러도 입력이 맞지 않으면 전송하지 않는다(`Controller.confirm`이 `confirmMatches()`를 다시 확인; 버튼 잠금을 우회한 호출 방지). 첫 포커스는 계속 취소 버튼이다(ADR 0004).
2. **활성화·롤백**: 대상 ID 입력을 없앤다. 확인 단계(이전 → 새 활성 릴리스, 되돌리는 방법 표시)에서 "실행" 버튼을 한 번 더 누르는 단순 확인만 한다. 첫 포커스는 활성화는 취소 버튼, 롤백은 사유 입력칸(필수 입력의 시작)이며 실행 버튼에는 가지 않는다. 롤백의 사유·근거 ID 필수(계약 `RollbackRequest`)와 `request_id` 멱등은 그대로다.
3. **방식이 다른 이유(E4)**: 승인은 보고서를 읽고 난 직후 한 건을 결정하는 모달 확인이다. 활성화·롤백의 확인 단계는 롤백에서 사유·근거·되돌아갈 대상 선택 같은 여러 입력을 받고, 현재 활성 릴리스와 이력 표를 보면서 입력해야 하므로 모달로 가리지 않고 같은 화면의 인라인 확인 단계로 둔다. 이 이유는 설계 판단이며 사용자 조사나 측정에 근거한 것이 아니다.

## 왜
- 파괴적(되돌릴 수 없는) 작업에 대상 이름을 입력하게 하는 확인 관행을 따른다. 표준 문서가 아니라 널리 쓰이는 UX 관행이다(GitHub 저장소 삭제 등, 원문 출처 문서는 없다). 확인 강도를 되돌릴 수 있는지에 맞추라는 것이 헤드 결정표 2절의 결정이다.
- 승인 ID 입력으로 우발 승인(Enter 연타, 습관적 확인)이 한 번 더 막힌다. 활성화·롤백은 되돌릴 수 있으므로 급할 때 입력 부담을 줄인다(ADR 0007이 감수 항목으로 적은 "급할 때 입력이 느려진다"를 해소).

## 검토한 대안과 버리는 이유
- 모두 ID 입력: 되돌릴 수 있는 롤백까지 느려진다(사고 대응 중).
- 모두 단순 확인: 되돌릴 수 없는 승인이 가장 약한 확인이 된다.
- 이중 승인(두 사람): 권한 모델이라 이 영역 범위 밖(deploy·헤드).

## 결과
- 얻는 것: 확인 강도가 위험도 순서와 같다. 시험: `tests/risk-confirm.test.ts`(승인·반려 ID 입력 전 전송 안 함, 버튼 잠금, 활성화·롤백 입력 없이 실행, 첫 포커스).
- 감수하는 것: 승인에 입력 한 번이 더 든다. 실제 브라우저에서의 포커스·키보드 동작과 승인 소요 시간은 확인하지 못했다(jsdom 시험만, ADR 0009).

## 되돌리는 조건
운영자가 제출 ID를 반복 복사해 형식적으로 넘긴다는 관찰이 있거나 이중 승인이 도입되면 바꾼다. 활성화가 되돌릴 수 없는 동작으로 바뀌면(예: 롤백 불가 릴리스) 활성화에도 입력 확인을 둔다.
