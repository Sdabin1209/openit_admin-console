# ADR 0020: `scripts/setup-env.sh`의 보고 한 줄과 멱등

- 상태: 채택(U43, 계약 v2.6.0). 환경 준비의 정본이 setup-env.sh라는 기존 결정(README 3절)을 이어 쓴다.

## 맥락
deploy가 이 영역의 `node_modules` 경로와 시험 도구(`npm test`)를 짐작해 doctor·전체 점검을 했다(구조 규칙 1 위반, OPEN_GAPS U43). 계약 v2.6.0은 영역이 준비한 환경과 시험 명령을 스스로 선언하는 `SetupEnvReport`를 정했다. 또 이전 `setup-env.sh`는 이미 준비돼 있어도 매번 `npm ci`를 돌려 `node_modules`를 지우고 다시 깔았다(계약: 이미 준비돼 있으면 아무것도 바꾸지 않는다).

## 결정
- 표준 출력의 마지막(이자 유일한) 줄에 `SetupEnvReport` JSON을 낸다: `{area, status, exit_code, seconds, environment{kind: node-modules, path: node_modules, test_command: ["npm","test"]}}`. 진행 기록은 모두 표준 오류다(`exec 3>&1 1>&2`, 보고만 fd 3). EXIT 트랩이 성공과 실패 모두에서 보고를 낸다.
- 멱등: `node_modules/.package-lock.json`이 `package.json`·`package-lock.json`보다 새것이면 `npm ci`를 생략한다.
- `test_command`는 `package.json`의 `scripts.test`와 같은 진입점(`npm test`)이다.

## 왜
- 계약 `SetupEnvReport` 설명이 정본이다. 값(상수와 숫자)만 담아 JSON 이스케이프가 필요 없다(`printf`).
- 멱등 판정은 npm이 설치 때 쓰는 숨은 잠금 파일의 수정 시각이다. npm 자신의 최신 판정이 같은 방식이다. 대안으로 `npm ci`를 항상 돌리면 오프라인에서 깨지고, 시험이 setup-env를 부르면 돌고 있는 시험 아래의 `node_modules`가 지워진다(이번 작업 중 실제로 일어났다). mtime 비교의 한계: 파일 시간이 어긋난 시스템에서는 불필요하게 다시 깔거나 낡은 환경을 최신으로 볼 수 있다. 이 가능성은 측정하지 않았다.
- 실패 보고에도 `environment`를 싣는다: 계약이 선택 필드로 허용하고, 환경이 일부 준비됐을 수 있어서가 아니라 모양을 하나로 두려는 것이다.

## 검토한 대안과 버리는 이유
- 보고를 별도 `--report` 모드로: 계약이 인자 없는 한 진입점을 정했다.
- 시험 명령을 deploy가 `package.json`에서 읽기: 이웃 파일 구조에 기대는 것이라 구조 규칙 1에 어긋난다.

## 결과
- 얻는 것: deploy가 `node_modules` 경로와 시험 도구를 짐작하지 않는다. 같은 환경에서 setup-env를 몇 번 불러도 변하지 않는다.
- 감수하는 것: 의존을 손으로 `node_modules`만 고친 경우 mtime 판정이 놓칠 수 있다(그때는 `node_modules`를 지우고 다시 부른다).

## 되돌리는 조건
계약이 보고 모양을 바꾸면(3.0.0에서 `environment` 필수 등) 이 ADR을 대체한다.
