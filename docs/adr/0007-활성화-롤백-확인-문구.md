# ADR 0007: 활성화·롤백은 대상 릴리스 ID를 입력해야 실행된다

- 상태: 채택(작업 단위 5, D85). 2026-10-29: 대상 ID 입력 요구는 [ADR 0014](0014-위험도에-맞춘-확인-강도.md)가 대체했다(사유·근거 필수, `request_id` 멱등은 유지).

## 맥락
활성 포인터를 바꾸면 서비스가 쓰는 모델이 바뀐다. 롤백은 사고 대응 중에 급하게 하는 일이라 실수 위험이 크다. 요청은 operator 역할 계정만 보낼 수 있다(서버가 403).

## 결정
확인 단계에서 대상 릴리스 ID를 그대로 입력해야 실행 버튼이 켜진다(`OpsController.confirmMatches`, 앞뒤 공백만 무시). 롤백은 사유와 근거 ID(1개 이상)가 필수이고, 대상 변경 시 입력이 비워진다. 같은 확인 단계의 재전송은 같은 `request_id`(멱등). 확인 단계에서 되돌리는 방법과 개인정보 금지 안내를 보인다.

## 왜
- 입력 확인 방식은 GitHub 저장소 삭제 등에서 널리 쓰이는 파괴적 작업 확인 관행을 따른 것이다. 표준 문서에서 가져온 것은 아니다(출처 문서 없음).
- 사유·근거 필수: 계약 `RollbackRequest`가 `reason`(minLength 1)과 `evidence_refs`(minItems 1)를 요구한다(`boundary-contracts/schemas/RollbackRequest.schema.json`).
- `request_id` 멱등: 계약의 `RollbackReceipt`가 `request_id`를 돌려주고 모의 서버가 같은 ID를 같은 결과로 처리한다. 실제 서버의 멱등 규칙은 **확인하지 못했다**(CR-004 4항).
- 활성화에 요청 ID·포인터 버전이 없는 것은 계약의 한계이며 CR-005로 제안했다.

## 검토한 대안과 버리는 이유
- 단순 확인 대화상자(예/아니오): 승인 화면과 같은 방식인데, 활성화·롤백은 다른 대상(릴리스)과 혼동할 수 있어 ID를 직접 쓰게 했다. 이 선택을 사용자 요구나 사고 사례로 뒷받침한 기록은 없다(근거 기록 없음).
- 이중 승인(두 사람): 이 영역 범위 밖(권한 모델은 deploy·헤드).

## 결과
- 얻는 것: 잘못된 대상 선택 방지, 롤백 사유 기록. 감수하는 것: 급할 때 입력이 느려진다(소요 시간 측정 안 함).

## 되돌리는 조건
운영자가 확인 문구를 반복 복사해 형식적으로 넘긴다는 관찰이 있거나, 이중 승인이 도입되면 바꾼다.
