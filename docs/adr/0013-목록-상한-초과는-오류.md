# ADR 0013: 목록이 20쪽을 넘으면 잘린 목록 대신 오류를 낸다

- 상태: 채택(2026-10-29, 표준성 점검 C5, 헤드 결정표 2절). [ADR 0010](0010-시간-제한과-한도-상수.md)의 "20쪽을 넘으면 오래된 릴리스가 목록에서 빠진다"를 대체한다.

## 맥락
릴리스 목록(`api/releases.ts`)은 20쪽(쪽 크기 500, 1만 건)까지만 읽고 그 뒤는 오류 없이 버렸다. 화면은 이 목록에서 현재 활성 릴리스의 위치를 찾아 활성화·롤백 후보를 자른다(`app/ops-controller.ts`의 `activateCandidates`, `rollbackCandidates`). 활성 릴리스가 잘린 부분에 있으면 `findIndex`가 -1이어서 활성화 후보가 전체 릴리스가 되고 롤백 후보는 없어진다. 실패 사례 목록(`api/cases.ts`)은 같은 상황에서 오류를 던져 두 목록의 동작이 달랐다.

## 결정
릴리스 목록도 실패 사례 목록과 같게 20쪽 안에 `next_cursor`가 null이 되지 않으면 `ApiError`를 던진다. 화면은 오류 상태가 되고 후보를 계산하지 않는다. 상한(20쪽)과 쪽 크기(500)는 바꾸지 않는다.

## 왜
- 조용한 데이터 손실 금지(헤드 결정표 2절). 계약 HTTP.md 공통 목록 규칙은 `next_cursor`가 null일 때까지가 전체이므로, 전체를 받지 못했다면 받은 것은 "전체 목록"이 아니다.
- 상한 값 20은 여전히 출처가 없다(ADR 0010). 값을 올리거나 없애는 대신 넘었을 때 알리는 쪽을 고른 이유: 서버가 같은 cursor를 반복해 돌려주는 경우 무한 반복을 막는 상한이 필요하고, 상한을 없애려면 중복 cursor 검출이 필요하다.

## 검토한 대안과 버리는 이유
- 상한을 없애고 끝까지 읽기: 서버 오류로 cursor가 순환하면 끝나지 않는다. 순환 검출을 새로 만들어야 한다.
- 계속 잘라서 돌려주고 화면에 경고 표시: 후보 계산이 틀린 목록에 의존하므로 경고만으로는 위험한 활성화·롤백 후보가 보인다.

## 결과
- 얻는 것: 잘린 목록으로 틀린 후보가 나오지 않는다. 두 목록의 동작이 같다. 시험은 모의 서버의 쪽 넘김(계약 규칙에서 도출)으로 3쪽은 끝까지 읽고 21쪽 분량은 오류를 내는지 본다(`tests/ops.test.ts`의 C5).
- 감수하는 것: 릴리스가 1만 건을 넘으면 릴리스 운영 화면을 쓸 수 없다. 실제 릴리스 수는 측정하지 않았다.

## 되돌리는 조건
릴리스 수가 상한에 가까워지면(운영에서 관찰되면) 서버 쪽 필터(예: 활성 릴리스 주변만 요청)를 계약에 요청하거나 상한을 근거 있는 값으로 바꾸는 새 ADR을 쓴다.
