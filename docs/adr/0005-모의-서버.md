# ADR 0005: 게이트·FailureStore·릴리스 운영의 모의 서버

- 상태: 채택

## 맥락
이웃 영역(release-gate, ops-feedback)의 코드를 읽거나 가져올 수 없고, 혼자 시험할 수 있어야 한다(워크스페이스 CLAUDE.md "이웃 영역의 메모리 구현으로 혼자 시험"). 이 영역은 SDK를 배포하지 않으므로 이웃의 가짜 SDK에 해당하는 것이 필요하다.

## 결정
`mock-server/`에 Node `http` 서버를 둔다. 시나리오는 제출·사례·릴리스 ID로 고른다(승인 대기, 자동 반려, 낡은 해시 409, 403, 느린 응답 등). 출력은 시험에서 `../boundary-contracts/schemas`로 검증한다(`tests/mock-conformance`, `ops-conformance`). 시각은 주입 가능(`now`), 시험은 고정 시계를 쓴다.

## 왜
- 브리프 2절이 모의 서버와 시나리오(승인 대기, 자동 반려, 사람 반려, 승인 완료, 낡은 `report_hash`, 403)를 요구한다.
- 스키마 검증을 시험에 붙여 모의 서버가 계약에서 멀어지는 것을 잡는다.

## 검토한 대안과 버리는 이유
- 시험마다 `fetch`를 가짜로 대체: 헤더·상태 코드·본문 흐름이 서버를 거치는 시험(`X-Openit-Report-Hash` 등)이 약해진다. 일부 단위 시험은 이 방식도 쓴다(`tests/flow.test.ts`).
- 실제 release-gate 사용: 이웃 코드 의존이라 금지.

## 결과와 한계
- 한계(확인): 모의 서버는 **계약 문서를 읽고 만든 것**이지 실제 서버가 아니다. 실제 release-gate가 `requested_by_role` 없는 본문, 409 조건, 릴리스 목록의 PASS 여부를 어떻게 처리하는지는 확인하지 못했다(CR-004). 모의 서버가 통과해도 실제 서버에서 통과한다는 뜻이 아니다.
- 스키마 검증은 모양만 본다. 의미 규칙(예: 서버의 `expected` 대조)은 모의에 일부만 있다.
- 지연 시나리오는 실제 `setTimeout`(`slowMs`, 시험 기본 150ms)을 쓴다. 시험은 조건 대기로 이 지연에 기대지 않게 했다.

## 되돌리는 조건
이웃 영역이 메모리 구현(가짜 SDK)이나 컨테이너 시험 서버를 배포하면 그것으로 대체하고 모의 서버를 줄인다.
