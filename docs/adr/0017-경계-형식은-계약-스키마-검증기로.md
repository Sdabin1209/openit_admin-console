# ADR 0017: 경계 형식은 계약 스키마로 만든 검증기로 검사한다

- 상태: 채택(작업 단위 U3, 계약 v2.2.1). 일부를 대체한다: ADR 0002의 검증 범위(검토자 입력 4종 -> 경계 형식 포함). 생성물 커밋 정책은 ADR 0002 그대로다.

## 맥락
D107로 이 영역이 주고받는 경계 형식 5종이 계약에 올랐다(`ApprovalRequest`, `ActivateRequest`, `CaseReviewRequest`, `ListEnvelope`, `OpsFeedbackDeidentifiedTrace`; 정본은 계약의 `conformance/promoted/admin-console.MANIFEST.json`). 코드는 그동안 키와 형식을 손으로 검사했다(`need(Array.isArray(d.items))`, `next_cursor ?? null`, trace는 객체인지만 확인). 손 검사는 계약이 바뀌면 조용히 어긋나고, `next_cursor`가 없거나 빈 문자열인 봉투를 끝으로 읽어 목록을 자르는 위험이 있었다.

## 결정
- `scripts/gen-schemas.mjs`가 위 5종과 `ImageLabels`를 Ajv standalone 검증기로 생성한다(`_common`은 `$ref` 해소용). 같은 단계에서 계약 `schemas_api.py`의 `PIPELINE_SCHEMA_VERSION`을 읽어 상수로 내보낸다.
- `api/contract.ts`가 보내기 전(`ApprovalRequest`, `ActivateRequest`, `CaseReviewRequest`)과 받은 뒤(`ListEnvelope`, `OpsFeedbackDeidentifiedTrace`)에 검사한다. 요청 위반은 보내지 않고 `INVALID_RECORD`로 던진다.
- 코드의 `pipeline_schema_version` 리터럴을 지우고 위 상수를 쓴다.
- 모의 서버 `trace()`는 계약 예시 모양(29개 키, 가명 ID, 값 자리 `[MASKED]`)으로 바꿨다.

## 왜
- 따른 규칙: 워크스페이스 CLAUDE.md(계약 스키마를 복사하지 않고 검증기로 쓴다), 구조 규칙 R6(영역 사이 형식의 정본은 스키마), R7(보증된 값을 다시 손으로 검사하지 않는다: `decide`의 `decision` 값 검사 등은 스키마가 하므로 지웠다).
- 스키마가 코드보다 엄격한 곳은 MANIFEST 주석대로 따른다: 승인 요청의 모르는 키 거부(`approver_id`를 싣지 않는다, D88), 활성화 본문의 행위자 이름 거부.
- 버전 상수를 손으로 복사하지 않는다: 복사하면 계약이 오를 때 어긋난다(모의 서버와 롤백 본문이 "2.0"이었고 계약은 "2.2"였다).

## 검토한 대안과 버리는 이유
- 손 검사 유지: 계약과 어긋나는 것을 시험으로만 잡는다. 이번 변경으로 시험이 계약 예시 전체를 검사한다.
- 런타임 컴파일: CSP 때문에 불가(ADR 0002).

## 결과
- 얻는 것: 계약 예시·`examples_invalid`가 그대로 시험의 기대값이다. 봉투 위반이 목록을 조용히 자르지 않고 오류가 된다.
- 감수하는 것: 서버가 계약보다 엄격하거나 느슨하면(trace에 모르는 키 등) 화면이 trace를 못 연다(BAD_RESPONSE). 실제 ops-feedback 서버의 출력은 확인하지 못했다. 생성물이 커진다(`generated/contract-validators.cjs`). 번들 크기 변화는 측정하지 않았다.

## 되돌리는 조건
계약이 브라우저용 검증기를 배포하면(ADR 0002 대안 b) 생성 단계를 그것으로 바꾼다. 실제 서버와 연동해 trace가 계약을 어기면 서버 쪽 수정 요청을 낸다(이 영역이 검사를 풀지 않는다).
