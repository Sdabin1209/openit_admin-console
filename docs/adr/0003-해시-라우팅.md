# ADR 0003: 해시(`#/...`) 라우팅

- 상태: 채택(설계서 1절)

## 맥락
한 페이지 앱이 세 화면(`#/`, `#/s/{id}`, `#/cases`, `#/cases/{id}`, `#/ops`)을 전환한다. 정적 서버(ADR 0006)가 파일 서빙만 하고 모르는 경로는 404를 낸다(`serve/static-server.mjs`). 앱은 게이트웨이 뒤에서 `/admin/` 같은 접두 아래에 놓일 수 있다(D70: 설정을 상대 경로 `config.json`으로 읽음, `app/config.ts`).

## 결정
`location.hash`로 라우팅한다(`app/main.ts`의 `route`). ID는 `encodeURIComponent`로 넣고 `safeDecode`로 풀며, 풀 수 없으면 오류 화면을 보인다.

## 왜
- 해시는 서버가 보지 않는다. 그래서 서버에 경로별 대체 응답(SPA fallback)이 필요 없고, 게이트웨이 접두가 무엇이든 같은 `index.html`로 동작한다.
- 따른 표준은 없다. 위는 이 구조(정적 서버 404, 접두 아래 배포)에서 도출한 이유다.

## 검토한 대안과 버리는 이유
- History API 경로: 정적 서버와 게이트웨이에 fallback 규칙이 필요하고 접두 처리가 얽힌다. 이 이유 외에 비교 기록은 없다(근거 기록 없음).
- 라우팅 없이 화면 상태만: 새로고침·링크 공유로 제출을 다시 열 수 없다.

## 결과
- 얻는 것: 서버 설정 없는 새로고침·북마크.
- 감수하는 것: 해시는 서버 로그에 남지 않는다(감사 로그 용도로는 쓸 수 없다). 제출 ID가 주소창에 보인다(환자 정보는 아님: 제출 ID는 후보 모델 제출의 식별자).

## 되돌리는 조건
경로별 서버 기능(서버 쪽 권한 검사, 로그)이 필요해지면 History API로 바꾸고 fallback을 둔다.
