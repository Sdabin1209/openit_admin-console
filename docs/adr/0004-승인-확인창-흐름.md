# ADR 0004: 승인 확인창 흐름(첫 포커스는 취소, 사유 필수, 해시 고정)

- 상태: 채택. 첫 포커스를 취소로 한 것은 전수 점검 지적(M4) 반영(작업 단위 6).

## 맥락
승인은 되돌릴 수 없고(확정 화면 문구: 확정하면 기록되고 되돌릴 수 없다) 사람의 판단이다. 화면은 합격/불합격을 판정하지 않는다(브리프 4절, D53).

## 결정
1. 승인·반려 버튼은 바로 보내지 않고 확인창(`<dialog>`)을 연다. 반려는 사유가 비면 확인창으로 가지 않는다.
2. 확인창이 열릴 때 포커스는 취소 버튼이다. 확정 버튼은 취소 다음 순서이고 기본 선택이 아니다.
3. 전송하는 `report_hash`는 승인자가 본 보고서의 응답 헤더 `X-Openit-Report-Hash` 값 그대로이다. 클라이언트는 해시를 계산하지 않는다.
4. 409 `STALE_REPORT`이면 보고서를 새로 불러오고 처음부터 다시 확인하게 한다(자동 재전송 없음). 전송 중에는 같은 제출+결정 요청이 하나만 나간다.

## 왜
- 1: 브리프 4절 "결정 전에 확인창을 거친다", "반려는 사유가 필수다".
- 2: Enter 연타나 습관적 확인으로 승인이 확정되는 것을 막으려는 것이다. 모달 대화상자는 보통 첫 포커스 가능 요소에 포커스가 가므로(브라우저 기본), 확정 버튼이 먼저면 Enter 한 번이 확정이 된다. 이 동작의 실제 브라우저 확인은 하지 않았다(jsdom 시험만: `tests/audit-ui.test.ts`).
- 3: HTTP.md I5(D69) "해시는 계산하지 않고 받은 값을 돌려보낸다". 해시 구현이 서버 한 곳에만 있어야 규칙이 어긋나지 않는다. 사람이 본 것과 승인된 것이 같은 보고서임을 서버가 대조한다.
- 4: HTTP.md D69의 409 `details.reason` 규칙. 재전송을 자동으로 하지 않는 것은 새 보고서를 승인자가 다시 읽게 하려는 것이다.

## 검토한 대안과 버리는 이유
- 확인 없이 즉시 전송: 되돌릴 수 없는 결정에 부적합.
- 클라이언트가 해시 계산: 규칙 중복과 어긋남 위험(D69에서 서버 한 곳으로 정함).
- 확인 문구 입력(ADR 0007 방식)을 승인에도 적용: 승인에는 입력을 더 요구하지 않았다. 이 판단의 근거는 측정이나 문서로 남아 있지 않다(근거 기록 없음).

## 결과
- 얻는 것: 우발 확정 감소, 바뀐 보고서에 대한 결정 차단.
- 감수하는 것: 클릭이 한 번 늘어난다. 서버가 같은 결정을 200으로 멱등 처리하는 것에 기댄다.

## 되돌리는 조건
승인 사고(우발 승인)가 관찰되면 확인 문구 입력을 승인에도 둔다. 실제 브라우저에서 포커스 동작이 다르게 확인되면 이 ADR을 고친다.
