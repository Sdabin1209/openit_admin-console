# ADR 0001: 프레임워크 없는 TypeScript SPA, esbuild 번들, tsc 타입 검사

- 상태: 채택(작업 단위 1부터)

## 맥락
사람이 쓰는 내부 운영 화면이다(출고 승인, 실패 사례 검토, 릴리스 운영: 화면 셋). 브라우저는 데스크톱, 한국어. 의존은 최소로 하고, 외부 CDN을 쓰지 않으며, 의존은 잠금 파일로 고정한다(`docs/brief.md` 4절·7절).

## 결정
- 언어는 TypeScript, UI 프레임워크 없이 직접 DOM(`app/views.ts`의 `h()`). 상태는 DOM 없는 컨트롤러(`app/controller.ts` 등)에 두고 뷰는 그것을 그린다.
- 번들은 esbuild 하나(`scripts/build.mjs`, 출력 `dist/app.js`), 타입 검사는 `tsc --noEmit`, 시험은 Node 내장 `node:test`.

## 왜
- 따른 기준: 브리프 7절 "기술 스택은 영역이 정한다. 의존은 최소로 한다", 4절 "외부 CDN을 쓰지 않는다(의존은 잠금 파일로 고정)". 설계서 6절이 같은 이유를 적었다.
- 화면이 셋이고 상태 기계가 컨트롤러에 있어, 프레임워크가 주는 것(컴포넌트 상태·재렌더 최적화)이 필요하지 않았다. 출력을 `textContent`/`setAttribute`로만 만들어 HTML 주입 경로가 없다(시험 `hygiene`이 `innerHTML` 사용을 소스에서 금지).
- esbuild는 TypeScript를 벗기고 번들 하나로 묶는 데 설정이 한 줄이다. 설정 파일이 필요한 번들러는 이 규모에 불필요하다고 판단했다.
- Node 24가 타입을 직접 벗기므로 시험·모의 서버에 별도 컴파일 단계가 없다(`package.json` engines `>=24`).

## 검토한 대안과 버리는 이유
- React/Vue 등: 의존과 빌드 설정이 늘고, 잠금·감사 대상이 늘어난다. 화면 셋에서 얻는 것이 없다고 판단. 번들 크기·개발 속도의 **비교 측정은 하지 않았다(측정 안 함)**. 그 밖에 이 대안을 따로 비교한 기록은 없다(근거 기록 없음).
- Vite/webpack: esbuild 단독으로 충분. 비교 측정 안 함.

## 결과
- 얻는 것: 런타임 의존 0(번들에 서드파티 코드 없음), 이미지가 작고 빌드가 빠름.
- 감수하는 것: 화면 갱신을 직접 관리한다. `app/main.ts`는 상태 서명 문자열을 비교해 다시 그리고, 다시 그리면 포커스를 잃어 수동으로 되돌린다(접근성 비용).

## 되돌리는 조건
화면이 대여섯 개를 넘거나 표·폼 상태가 서로 얽혀 직접 DOM 갱신 코드가 컨트롤러보다 커지면 프레임워크를 다시 검토한다. 새 ADR이 이 문서를 대체한다.
