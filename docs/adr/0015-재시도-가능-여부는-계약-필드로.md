# ADR 0015: 재시도 가능 여부는 `BoundaryError.retryable`을 쓴다

- 상태: 채택(2026-10-29, 표준성 점검 C9, 헤드 결정표 2절)

## 맥락
`api/http.ts`의 `toError`는 응답 본문의 `retryable`을 읽지 않고 상태 코드(`UNAVAILABLE`이거나 5xx)로 다시 판정했다. 계약은 "호출자는 `code`와 `retryable`로만 행동한다"(`CONVENTIONS.md` 오류 절)고 하고, `BoundaryError`의 `retryable`은 필수 boolean이다(`schemas/BoundaryError.schema.json`).

## 결정
본문에 boolean `retryable`이 있으면 그 값을 쓴다. 본문이 `BoundaryError`가 아닐 때(게이트웨이가 낸 502 HTML 등)만 계약 HTTP.md 공통 절의 "네트워크 오류와 5xx와 503은 `UNAVAILABLE`(재시도 가능)"로 대신한다.

## 왜
- 계약 준수(R7). 같은 `code` 안에서 사유에 따라 재시도 가능 여부가 달라질 수 있다(`CONVENTIONS.md` 88행: 409 `CONFLICT`의 `TURN_IN_PROGRESS`). 상태 코드로 재판정하면 서버의 의도를 버린다.
- 본문이 없는 경우의 대체 규칙은 화면이 만든 규칙이 아니라 HTTP.md 문장에서 가져왔다.

## 검토한 대안과 버리는 이유
- 상태 코드 판정 유지: 계약과 어긋난다.
- 본문이 없을 때도 재시도 불가로 둠: 게이트웨이가 5xx를 낼 때 사람에게 "다시 시도"를 안내하지 못한다. HTTP.md가 5xx를 재시도 가능으로 정했다.

## 결과
얻는 것: 서버가 낸 재시도 신호를 그대로 따른다. 시험: `tests/retryable.test.ts`(기대값은 계약 문장에서). 감수하는 것: 화면은 자동 재시도를 하지 않으므로(사람에게 안내만) 이 값은 안내 문구 선택에만 쓰인다.

## 되돌리는 조건
계약이 `retryable` 의미를 바꾸면 새 ADR로 대체한다.
