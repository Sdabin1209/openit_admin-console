# ADR 0002: 계약 검증기를 스키마에서 생성하고 생성물을 커밋

- 상태: 채택. 단 '생성물 커밋 허용 여부'는 헤드 결정 대기(CR-003 4절). 대상이 `survey-schema` 검증기에서 `boundary-contracts` 검증기로 바뀐 것은 계약 2.0.0 정렬(작업 단위 3).

## 맥락
실패 사례 검토 화면은 검토자가 쓴 `reviewed_input`·`expected`를 전송 전에 계약 스키마(`ActionExtractionInput`, `ActionExtraction`, `ResponseRequest`, `ResponseText`)로 검증한다. 서버가 400으로 거절하기 전에 화면에서 알리려는 것이다. 브라우저 CSP는 `script-src 'self'`라 `eval`/`new Function`이 막혀 Ajv를 런타임에 컴파일할 수 없다(`serve/static-server.mjs`의 CSP).

## 결정
`scripts/gen-schemas.mjs`가 `../boundary-contracts/schemas`를 읽어 Ajv standalone 코드를 만들고 `generated/contract-validators.cjs`로 **커밋**한다. 스키마 JSON의 복사본은 리포에 두지 않는다. 시험(`tests/schemas-generated.test.ts`)이 원본이 있을 때 생성물이 원본과 같은지, 복사본이 없는지 확인한다.

## 왜
- 따른 규칙: 워크스페이스 CLAUDE.md "스키마는 복사본을 만들지 않는다", 계약은 계약 패키지에서 가져온 것만 쓴다. 손으로 쓴 검증 코드는 계약과 어긋날 수 있어 버렸다.
- 생성물을 커밋하는 이유: 이미지 빌드(CI)에는 `../boundary-contracts`가 없다(Dockerfile은 `COPY generated`만 한다). 생성 단계를 CI에 두려면 계약 리포 접근이 필요하다.
- CSP를 완화하지 않으려고(`unsafe-eval` 금지) 미리 컴파일한 코드를 쓴다.

## 검토한 대안과 버리는 이유
- (a) 런타임 Ajv 컴파일: CSP에서 불가. CSP 완화는 보안 이득을 버리므로 선택하지 않음.
- (b) boundary-contracts가 브라우저용 검증기를 패키지로 배포: 더 낫다고 보지만 계약 리포의 결정이라 CR-003에서 헤드에게 제안했다(미정).
- (c) 검증을 서버에만 맡김: 화면이 없어도 동작하지만 검토자가 400 문구만 보게 된다. 서버는 어차피 최종 검증을 한다(화면 검증은 편의).

## 결과
- 얻는 것: 계약과 같은 규칙, CSP 유지, 복사본 없음.
- 감수하는 것: 생성물이 커밋되어 계약이 바뀌면 재생성을 잊을 수 있다(시험이 원본이 있는 환경에서 어긋남을 잡는다. 원본이 없는 환경에서는 건너뛴다). 생성물에 스키마가 내장된다.

## 되돌리는 조건
헤드가 (b)를 채택하면 생성물과 스크립트를 없애고 패키지 검증기를 쓴다. 커밋 금지로 정하면 CI에서 생성한다.
