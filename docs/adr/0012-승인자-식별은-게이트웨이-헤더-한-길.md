# ADR 0012: 승인자 식별은 게이트웨이의 `X-Openit-User` 한 길

- 상태: 채택. ADR 0006의 개발용 `/config.json`을 대체(Supersedes 일부)한다.

## 맥락
이전에는 개발 모드에서 환경 변수 `ADMIN_DEV_APPROVER_ID` -> 정적 서버 `/config.json` -> 화면 -> 승인 본문 `approver_id`라는 두 번째 길이 있었다. 계약 HTTP.md I5(D88)는 승인자를 게이트웨이가 붙이는 `X-Openit-User` 헤더로만 정하고, 헤더가 없으면 401, 본문 `approver_id`는 무시하며 헤더와 다르면 거부한다. 그래서 두 번째 길은 실제 release-gate에서는 401이 되는 계약 밖 경로였다(점검 AC-02).

## 결정
화면은 승인 본문에 `approver_id`를 싣지 않는다. `ADMIN_DEV_APPROVER_ID`, `/config.json`, `app/config.ts`를 없앤다. 개발·시험은 HTTP.md I5의 문장("개발·시험은 시험용 게이트웨이나 시험 헤더를 붙여 호출한다")대로, 모의 서버가 게이트웨이를 흉내 내어 `X-Openit-User`를 붙인다(`mock-server/main.ts`의 `gatewayUser`). 모의 서버도 계약대로 헤더가 없으면 401, 본문 값이 헤더와 다르면 400으로 거부한다.

## 왜
- 표준(계약)이 이미 한 길을 정했다: HTTP.md I5, CONVENTIONS 9절. 본문 값은 위조할 수 있다는 것이 계약이 든 이유다.
- 실제 서버와 다르게 동작하는 개발 경로는 시험이 통과해도 운영에서 실패하게 만든다.

## 검토한 대안과 버리는 이유
- 개발 모드 유지: 계약 밖 설정 경로(환경 변수 -> `/config.json`)가 이 영역에만 생기고 실제 서버에서 401이 되므로 버림.

## 결과
얻는 것: 개발과 운영의 승인 경로가 같다. 감수하는 것: 모의 서버 없이 이미지를 단독으로 띄우면 승인 호출은 게이트웨이가 없어 실패한다(원래 `/v1`은 게이트웨이 몫).

## 되돌리는 조건
계약이 승인자 식별 방식을 바꾸면(예: 본문 값을 받게 되면) 이 결정을 새 ADR로 대체한다.
