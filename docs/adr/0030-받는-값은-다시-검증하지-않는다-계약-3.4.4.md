# ADR 0030: 계약에서 이 영역이 받는 값은 다시 검증하지 않고, 만드는 값만 보내기 전에 검증한다

- 상태: 채택(2026-11-04, 계약 v3.4.6 코드 단계). ADR 0017의 검증 범위를 좁힌다.

## 맥락
ADR 0017은 응답까지 계약 스키마(읽기용 투영)로 검사했다. 계약 CONVENTIONS 3절(생산자 출력 검증)과 ADR 0010 R7은 값을 만드는 쪽이 내보내기 전에 검증하고 받는 쪽은 다시 검증하지 않는다고 정한다. 이 영역은 `x-consumers`에 있는 값(목록 봉투, 제출·판정·릴리스·결과·사례·trace, SSE 이벤트, userinfo)을 받고, `x-producers`에 있는 값(`ApprovalRequest`, `ActivateRequest`, `RollbackRequest`, `CaseReviewRequest`, `PushSubscriptionRequest`)을 만든다.

## 결정
- 만드는 값 5종은 보내기 전에 계약 검증기로 검사하고 어기면 보내지 않는다(`INVALID_RECORD`). `PushSubscriptionRequest`를 더했다(endpoint는 https·443만, SSRF 방지, RUNTIME R3.18).
- 받는 값은 `link_*`에서 스키마로 다시 검사하지 않는다. 응답과 요청이 같은지 맞춰 보는 검사도 지웠다. 읽기용 투영 타입은 화면이 읽는 필드의 모양일 뿐이다.
- SSE 이벤트·userinfo의 타입은 계약 `ResultReadyEvent`·`HeartbeatEvent`·`HumanUserInfo`에서 생성하고 내부 사본(`ResultReady`, `UserInfo`)은 지웠다. 로그인 경로 값은 `HumanAuthEndpoints` 타입으로 선언해 계약이 바뀌면 컴파일이 실패한다.

## 왜
계약이 정한 책임 분담(R7)이다. 받는 쪽이 다시 검사하면 생산자의 결함을 받는 쪽이 가려 주어 어디가 틀렸는지 흐려진다.

## 검토한 대안
- 계속 검사: 계약이 금지하지 않지만 정본 규칙과 어긋난다. 서버가 새 필드를 더한 날 화면이 멈추는 위험도 있다(ADR 0017 감수 사항).

## 결과
얻는 것: 코드 단순화, 계약과 같은 책임 분담. 감수하는 것: 서버가 모양을 어기면 화면이 오류 안내 대신 빈 값을 보일 수 있다(생산자 결함으로 보고 서버에서 고친다).

## 되돌리는 조건
계약이 받는 쪽 검증을 요구하면 되돌린다.
